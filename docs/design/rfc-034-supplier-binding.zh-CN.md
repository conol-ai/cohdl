# RFC-034：带贴片坐标映射的供应商绑定

> 中文版，以英文版 [`rfc-034-supplier-binding.md`](rfc-034-supplier-binding.md) 为准。
>
> 草案。编号为临时编号，待中央登记分配；错误码同样为临时编号，待统一分配。基线：main `329af05`（2026-10-21）。建立在以下基础之上：临时的 `part`/AVL 语法（`docs/provisional-syntax.md` §2）、RFC-001（单位）、RFC-020/025/026（放置、旋转、背面贴装）、RFC-029/030（版本化包、registry.cohdl.org），以及对 RFC-030/DR-036 的 registry 搜索修订。同时与两个没有 RFC 的仓库扩展（提交 `f1f7acc`）配合：零件标记 `#[source_unspecified("mpn"|"mfr")]`，允许主料条目显式留空 `mpn` 或 `mfr`；以及 `cohdl build --logical-only`，只写逻辑产物、不写物理产物。

## 问题

CoHDL 的零件用厂商和 MPN 说明"买什么"。但贴片厂和分销商是按它们自己的料号下单，按它们自己的封装坐标系贴片，而 CoHDL 两者都表达不了。

- **没有供应商料号。** AVL 条目只有 `mfr`、`mpn` 和 `footprint`，其他键会被 `src/check/generics.rs` 以 E802 拒绝。即使在同一家供应商那里，一个 MPN 也可能对应多个料号；本 RFC 的调研就发现某射频连接器的 MPN 在同一家分销商下有两个料号。所以 BOM（`src/emit/bom.rs`）上传给贴片厂之前，必须有人手工对料。现有的 `.enet` 网表输出也因为没有数据可填，省略了该格式的供应商属性（记录在 `docs/compliance-report.md` 中）。
- **没有贴片坐标映射。** 贴片厂用它自己库里的封装来贴每个零件，这些封装的原点和 0° 方向往往和设计里的封装不同。坐标文件（CPL）如果直接报设计自己的位置和角度，零件就会贴偏或贴转。`tools/smt_pos.py` 明确把这件事留给"贴片厂自己的修正表"，而这张表在设计之外，不会和设计一起做版本管理。
  - 拿官方库对照一家贴片厂的封装库实测：33 个零件中有 14 个的 0° 方向不同。
  - 偏移和旋转取决于一对东西：这个封装，以及该供应商料号在该供应商那里对应的封装。所以不能做成一张全局表。
- **看不到零件在哪里能买到。** registry.cohdl.org 显示零件的 MPN，但无法链接到供应商页面，也无法显示供应商有没有货。

面向的人群：
- 为设计挑选"真能下单"零件的 AI 作者。
- 希望从零件一键跳到供应商页面的审阅者。
- 要把设计交给贴片厂的人，他们需要不经手工修改、对这家贴片厂就正确的 BOM 和坐标文件。

## 目标

- **把供应商绑定到 AVL 条目上。** 任何 AVL 条目都可以为任意多个供应商写明：该供应商的料号，以及从本条目封装到该供应商封装的变换（偏移和旋转）。
- **编译器保持供应商中立。** 编译器只检查结构和单位，不认识任何具体供应商。与供应商相关的知识（料号格式、商品页链接、目录分类）放在 registry 的数据和工具里。
- **输出贴片坐标文件和按供应商的文件。** 对任何有放置信息的设计，`cohdl build` 输出与供应商无关的贴片坐标文件（CPL）。对每个选定的供应商，还输出以该供应商料号为键的 BOM、映射文件和该供应商的坐标文件，全部按一条确定的组合规则换算。
- **在 registry 里展示供应商。** registry 为每个零件显示它的供应商、料号、链接，以及在有目录快照时的供货情况。可以按供应商、按供应商自定义的分类搜索，还可以在线核对一个项目的绑定。
- **服务于宪章（Constitution）的优先级** 第 1 位（正确性/可判定性）、第 2 位（可被 AI 生成）和第 5 位（忠实输出）。

## 不做的事

- **不在语言里内置任何具体供应商。** 不把任何供应商名称、料号格式或链接编译进 `cohdl`。
- **包里不放实时供应商数据。** 库存、价格、分类每天在变。它们放在 registry 里并标注日期，绝不写进 `.cohdl` 源码。
- **不用供应商的几何数据。** 绑定只记录供应商封装相对设计自身封装的位置关系。设计的封装几何仍然依据厂商文档编写（见 `LIBRARY.md`）。
- **不做封装级的默认映射。** 绑定按 AVL 条目和供应商逐一给出。让同一封装的所有零件共用一个映射，推迟到以后（见"备选方案"）。
- **不自动选料、不自动替换、不修改源码。**
- **不下单，也不向供应商上传文件。**
- **不包含官方库自己的供应商计划**：给现有官方零件回填供应商料号、调整官方封装使某个选定供应商的映射为 (0, 0, 0°)、按目录清单补料。这项工作使用本 RFC 的机制，由库计划和 `LIBRARY.md` 维护，不属于语言设计。

## 设计

### 1. 供应商子句

AVL 条目（`primary { … }` 或 `alt { … }`）中可以有零个或多个供应商子句，和条目里其他项一样用逗号分隔：

```text
supplier SUPPLIER "PART_NUMBER" [at (X, Y)] [rotate ANGLE]
```

```cohdl
pub part RP2350A_QFN60: RP2350A {
    primary { mfr: "Raspberry Pi", mpn: "RP2350A", footprint: qfn::QFN60N40P700X700_1EP340X340,
              supplier acme "A-104411" }
}

// Only the Samsung alternate is bound, so a supplier BOM for acme orders
// it; it carries its own (here identity) mapping.
pub part C_100n_16V_X7R_0402: MLCC<100nF, 16V, 10%>[C0402] {
    primary { mfr: "Yageo", mpn: "CC0402KRX7R7BB104", footprint: CHIP_0402 }
    alt { mfr: "Samsung", mpn: "CL05B104KO5NNNC", supplier acme "A-200157" }
    alt { mfr: "Murata", mpn: "GRM155R71C104KA88D" }
}

// Mapping values illustrative: the supplier's footprint for this part is
// turned half a revolution and its origin sits 1.2 mm off ours.
pub part CONN_BAT_2P: BAT_CONN_2P {
    primary { mfr: "JST", mpn: "S2B-XH-A(LF)(SN)", footprint: FP_BAT_2P_2P5,
              supplier acme "A-300931" at (0mm, -1.2mm) rotate 180 }
}

// Several suppliers on one entry, each with its own part number and
// mapping. `--supplier acme` and `--supplier globex` produce different
// BOMs and CPLs for the same board.
pub part USB_C_HRO_TYPE_C_31_M_12: USB_C_Receptacle_2_0 {
    primary { mfr: "HRO", mpn: "TYPE-C-31-M-12", footprint: FP_USB_C_Receptacle_HRO_TYPE_C_31_M_12,
              supplier acme "A-165948" at (0mm, 0.5mm) rotate 180,
              supplier globex "GX-31M12-T" rotate 90 }
}
```

（示例中的英文注释保持原样。四个示例分别是：主料自带绑定；只有 Samsung 替代料有绑定，所以 acme 的 BOM 订的是它，它带有自己的映射，这里是恒等映射；连接器的映射值仅为示意，表示该供应商的封装转了半圈，原点相对我们的封装偏了 1.2 mm；同一条目绑定两家供应商，各有自己的料号和映射，`--supplier acme` 和 `--supplier globex` 会为同一块板生成不同的 BOM 和坐标文件。）

规则：

- **`SUPPLIER`** 是一个标识符：以小写 ASCII 字母开头，后面跟小写字母、数字或 `_`，最长 32 字节。这个集合是**开放的**：编译器不赋予任何具体名字含义。约定俗成的名字记录在 registry 的供应商表里（§4），不在编译器里。本 RFC 中的 `acme`、`globex` 及其料号均为虚构的占位示例。`mpn` 和 `mfr` 两个 ID 保留不用（E813）：它们的大写形式会和 KiCad 网表里的 `MPN`/`MFR` 字段重名（§3.3）。
- **`PART_NUMBER`** 是一个字符串：去掉首尾空白后不能为空，最长 128 个 UTF-8 字节，不含控制字符。编译器不做任何供应商特有的格式检查。
- **`at (X, Y)`** 是映射偏移，由两个 `Length` 值组成（RFC-001；写裸数字会报现有的单位错误）。可以为负数，默认为 `(0mm, 0mm)`。
- **`rotate ANGLE`** 是映射旋转，为 `0..=359` 范围内的整数度。取值范围和诊断形式与 `place … rotate` 以及（现行任意角度偏离规则下的）焊盘旋转相同。默认为 `0`。
- **复用现有语法。** `at (…)` 和 `rotate …` 是现有的放置子句，按 §2 定义的含义复用。`supplier` 只在 AVL 条目内一项的开头被识别：其后紧跟一个标识符和一个字符串，而不是 `:`。所以它是上下文关键字，不新增保留字；在其他任何地方，名为 `supplier` 的现有标识符照常可用。
- **唯一性：**
  - 同一条目不能重复写同一个供应商。
  - 在整个参与编译的包集合里（所有 `part` 的主料和替代料，与 `src/check/generics.rs` 中现有的跨 part `(mfr, mpn)` 身份检查扫描范围相同），同一个（供应商, 料号）——料号按原样逐字比较，不去空白、不折叠大小写——不能出现在（`mfr`, `mpn`）不同的两个条目上，因为一个供应商料号只对应一种货品。显式留空（来源未给出）的 `mpn` 视为与任何非空 `mpn` 都不同：如果和别的条目共用料号，就等于悄悄断言了那个未知的 MPN。
  - 两种情况都报 **E813**。
- **数量上限。** 每个 AVL 条目最多 16 个供应商子句（超出报 E813）。registry 索引采用同样的上限。
- **MPN 未知。** 在 `#[source_unspecified]` 下 `mpn` 或 `mfr` 显式留空的主料条目，也可以和其他条目一样带供应商子句。对这类零件，供应商料号可能是唯一能用来下单的身份，绑定把它记录下来，而不去猜 MPN。该标记自身的规则不变；供应商子句既不能满足它，也不能取代它。
- **可选。** 没有任何供应商子句的零件也是合法的；不请求供应商输出时，`check`/`build` 的行为和现在完全一样。

诊断：
- **语法错误**（缺少供应商标识符或料号字符串、多余的记号）由解析器报 **E010**，和其他所有语法错误一样。
- **E813** 负责子句的语义，并指明零件、条目和供应商：料号为空、超长或含控制字符，供应商标识符超长，供应商重复，料号冲突，子句超过 16 个，角度越界，以及 `at` 中的值不是 `Length`（裸数字或其他单位）。现有各结构都自己负责单位错误（焊盘是 E805/E806，`place` 是 E1007），这里同样由 E813 负责。
- 词法层面的单位错误（E101、E103、E104）照常适用。
- 未知的 `name:` 键仍然报 E802。

### 2. 映射的含义

绑定里的映射说明：把该料号在供应商那里的封装画进本条目封装的坐标系时，它位于何处。

- `at (dx, dy)` 是供应商封装原点在本条目封装局部坐标系中的位置。
- `rotate r` 是供应商封装 0° 轴在同一坐标系中的角度，角度正方向与焊盘旋转（RFC-025）相同。

因此，供应商封装的局部点 `q'` 对应本条目封装的局部点 `q = d + Rot(r)·q'`，其中 `d = (dx, dy)`。

**规范定义。** 一个实例的供应商贴片位置为：

```text
supplier_place = compose_place(instance_place, PlaceData { at: d, rotate: r, side: Top })
```

其中 `compose_place` 就是编译器现在用来把 subdesign 内部放置与其使用处组合起来的函数（`src/check/expand.rs`）。它会移到共享模块，让 CPL 输出和 subdesign 组合使用同一份实现，不会各自漂移。它同时覆盖两面：在底面（RFC-026）先镜像偏移的 x，再旋转，并反转映射旋转，和放在底面的 subdesign 内部的放置完全一样。所有运算都在 `src/trig.rs` 中完成，绝不使用平台浮点三角函数，以保证输出逐字节稳定。

**直观理解（顶面）。** 对于放置在 `P`、旋转为 `θ` 的实例：

```text
P_s = P + Rot(θ) · d
θ_s = (θ + r) mod 360
```

`P`、`d` 和 `Rot` 都在编写坐标系中（+y 向下），正角度从上往下看是逆时针，即 `place … rotate` 的方向。在这个坐标系里，`Rot(θ)` 等于 `trig::rotate(·, (360 − θ) mod 360)`，因为 `trig::rotate` 是在 +y 向上的坐标系中逆时针旋转。正因为符号容易弄反，规范引用的是 `compose_place`，而不是公式。

映射为 `(0, 0, 0°)` 表示供应商封装的坐标系与本条目封装的坐标系完全相同。

### 3. 构建输出

下面的 CPL 文件和 `.kicad_mod`、IPC-2581 一样属于**物理**输出：只在物理构建中、且现有的物理导出检查（`emit::validate_physical_export`）通过之后才写出，因此被该检查拒绝的设计不会得到 CPL。`cohdl build --logical-only` 下不写任何 CPL，也不报 E815。供应商 BOM 和映射文件与普通 BOM 一样属于采购数据，两种模式下都会写出。

**文件归属。** 所有新文件都通过现有的 `write_artifact` 写出，并和其他产物一样记入 `out/.cohdl-manifest`。因此：
- 如果已存在一个同名、但不是 CoHDL 写的文件，构建会失败，和现在一样；
- 本次构建不再产出的文件会被过期清理删除，例如去掉 `--supplier acme` 后的 `-acme-*` 文件，或删掉最后一个 `place` 后的 CPL。不会残留过期的采购文件。

`build --json` 的 `build` 对象新增 `cpl`（路径）和 `suppliers`（`{ "<ID>": { bom, map, cpl? } }`）两个键，只在写出相应文件时出现。

#### 3.1 中性贴片坐标文件（不指定供应商）

只要设计中至少有一个实例用 `place` 放置（RFC-020/025/026，包括经 `subdesign` 组合得到的放置），`cohdl build` 就写出 `out/<name>-cpl.csv`。这个文件与供应商无关：它报告设计自身的封装坐标系，不套用任何映射。

```text
Designator,Mid X,Mid Y,Layer,Rotation
```

- **行：** 每个**需要机器贴装的实例**一行：在 BOM 中有对应行、且封装的 KiCad 焊盘投影（§3.2 映射文件）中至少有一个带编号的 `smd` 焊盘的实例。纯通孔和没有焊盘的实例不写入。
  - 判断依据是投影而不是源码焊盘，这样只能看到板子的 `tools/smt_pos.py --neutral` 也能得出同样的结论。两者有两处不同：环形焊盘总是写成 SMD 焊盘；锡膏开窗是不带编号的 SMD 焊盘，不计入，即使它出现在为通孔回流（pin-in-paste）加了锡膏的通孔件上。
  - 不按元件值或位号排除。买了的料就要贴。
  - `tools/smt_pos.py` 现有的默认输出还会按经验规则排除值为 `TouchSensor`/`TouchPad` 的封装和 `TP…` 开头的位号。这些排除只保留在旧的默认输出里，`--neutral` 严格按本规则输出。
  - 怎样标记"采购但不贴装"的实例，不在本 RFC 范围内。
  - 一致性测试覆盖四种情况：贴片器件、同时有贴片和通孔焊盘的连接器、测试点、裸铜器件。
- **原点：** 设计声明了 RFC-020 板框时，取板框外接矩形的左下角，Y 轴向上，与 `tools/smt_pos.py` 现在用的原点相同；没有板框时，取编写坐标系原点，y 取反。
- **位置：** `Mid X`/`Mid Y` 是**封装原点**，单位毫米，固定写四位小数（四舍五入，远离零方向），带 `mm` 后缀（如 `12.3450mm`）。它不是焊盘质心，因为 §2 的映射是在两个封装原点之间定义的。
- **层：** `Top` 或 `Bottom`。
- **旋转**，范围 `0..=359`：
  - 顶面：`place` 的旋转角。
  - 底面：KiCad 对该零件使用的封装角度，对 `place … rotate R side bottom` 即 `(R + 180) mod 360`。这正是 `--emit kicad_pcb` 写出的值，也是从该板子导出坐标时报告的值。用同一套约定，编译器 CPL 和从板子导出的 CPL 就完全一致。一致性测试会在输出的板子上，把顶面和底面两种情况都对照 `tools/smt_pos.py` 的输出固定下来。
- **未放置的实例：** 需要机器贴装但没有放置的实例不写入；构建只报**一条 E815** 警告，给出数量并列出它们的位号。部分放置的设计很常见，这样只会多一行，而不是每个零件一行。编译器只是临时摆放的位置（如 `--emit kicad_pcb` 对未放置零件的临时排布）绝不写入。
- **排序：** 各行按位号自然顺序排列，输出逐字节稳定。
- 设计中没有任何 `place` 语句时，不写 CPL 文件，也不报警告。设计中至少放置了一个实例时，即使没有任何行（例如放置的都是通孔件）也写出文件，只有表头。
- **未放置**指实例在设计自己的布局里没有位置（`place`，包括经 `subdesign` 组合得到的放置）。输出器自己安排的暂存位置不算放置。

如果最终布局在 CoHDL 之外完成，坐标文件改由布局完成的板子生成。`tools/smt_pos.py` 新增 `--neutral`，按上面的列、原点、位置和旋转约定写出文件。它现有的默认输出（11 列、`Mid X/Y` 为焊盘质心、层写作 `T`/`B`）对现有用户保持不变。

#### 3.2 按供应商输出（`--supplier ID`）

`cohdl build --supplier ID`（可重复，每个 ID 一套文件）写出：

| 文件 | 内容 |
|---|---|
| `out/<name>-<ID>-bom.csv` | 表头为 `Comment,Designator,Footprint,<ID> Part #`，最后一列表头是大写的供应商 ID（`acme` 即 `ACME Part #`）。每个选定的采购身份一行（见下文）。 |
| `out/<name>-<ID>-map.json` | `schema_version: 2`。包含 `bottom_rotation`（`"kicad"` 或 `"mirrored"`，即本次构建为供应商 CPL 采用的约定，使套用映射文件的工具写出相同的角度），以及 `footprints` 和 `designators` 两张表（见表格后的说明）。 |
| `out/<name>-<ID>-cpl.csv` | 在写出中性 CPL（§3.1）时一并写出，因此 `--logical-only` 下从不写出。列、行和原点都与中性文件相同。每行的放置先用该位号的映射按 §2 换算，底面行再按本次构建为 `ID` 指定的 `bottom_rotation`（见下文）处理。 |

中性的 `-cpl.csv` 照常写出；`--supplier` 只会增加文件，不会替换任何文件。`--supplier` 可以和 `--logical-only` 同时使用（它不是 `--emit` 的取值），此时只写 BOM 和映射文件。

**底面角度约定。** 语言和中性 CPL 中的所有角度都使用 KiCad 的约定（§3.1）。如果贴片厂读取底面角度的手性相反，在导出时用参数指定，而不是写进源码：

```sh
cohdl build --supplier acme --bottom-rotation acme=mirrored
```

- `--bottom-rotation ID=VALUE` 可重复，每个 `ID` 最多一次，且 `ID` 必须同时由 `--supplier` 给出。其他情况（未知取值、`ID` 重复或未被选中）都是用法错误，退出码 2，在构建开始之前报出。
- `kicad`：不给该参数时的默认值。供应商 CPL 的底面行使用 §3.1 的角度。
- `mirrored`：该供应商 CPL 的底面行使用 `(180 − θ) mod 360`，θ 是映射后放置在 §3.1 下的角度。对映射为恒等的 `place … rotate R side bottom`，结果是 `(360 − R) mod 360`，即从底面看过去的角度。
- 位置、面别、顶面行、中性 CPL 和各 BOM 都不受影响。映射文件记录该取值（`--logical-only` 下也记录），因此 `tools/smt_pos.py --map` 从布局完成的板子上能得到相同的角度，无需再给一次参数。
- 构建的文字输出在每个写出的供应商 CPL 旁注明所用约定，`build --json` 以 `suppliers.<ID>.bottom_rotation` 给出。

之所以用参数而不用映射，是因为这个差值取决于零件自身的角度：某一家贴片厂的预览（见"待定问题"）读取底面角度的约定只在 90° 和 270° 时与 KiCad 一致，任何固定的 `rotate` 都无法抵消。之所以不放进语言，是因为它描述的是导出目标，而不是设计本身；编译器依然不为任何供应商名称赋予含义（见"备选方案"第 5 条）。

**映射文件。** 映射文件记录了每个映射是针对哪个封装坐标系写的，这样把它套用到已布局板子的工具就能判断板子上用的是否还是那个坐标系。
- `footprints`：`designators` 中每个实例所用的封装各一项，以完整路径为键。每项包含：
  - 所属包及其版本；
  - `pads`：该封装的 **KiCad 焊盘投影**，每个焊盘写成 `[编号, x, y]`，为规范 mm 字符串，依次按编号、x、y 排序。这个顺序只用于规范序列化和 `frame` 哈希，下面的坐标系检查不按它配对；
  - `frame`：上述 `pads` 列表规范 JSON 形式的 SHA-256。

  映射文件顶层另有 `pad_projection: 1`，表示下面这套投影规则的版本。

**焊盘投影。** `pads` 记录的是板子上看到的焊盘，因为读取已布局板子的工具只能拿这个来比较。它取自 `.kicad_mod` 和 `--emit kicad_pcb` 已经共用的推导（`kicad_mod::pad_plans`），所以映射文件和板子不会各自漂移。不使用源码焊盘列表：投影和它有几处不同，直接比较会把正确导出的板子判为不一致。
- **只列带编号的焊盘。** 投影还会写出不带编号的焊盘：锡膏覆盖开窗（RFC-018，包括分割环形锡膏的每一段）和安装孔（RFC-022/023）。它们没有电气身份，比较时双方都排除。
- **位置是 KiCad 锚点**，在封装的正面局部坐标系中（+y 向下）。多数焊盘的锚点就是源码写的中心。环形焊盘的锚点被移到铜环上，即沿焊盘自身 +x 轴偏移 `mid_radius`；映射文件记录的是这个锚点，不是环心。
- **重复的焊盘编号**（一个引脚对应多个焊盘）每个焊盘各出现一次，所以这个列表是多重集合。
- 如果改变了 `pad_plans` 放置锚点的方式或给哪些焊盘编号，所有受影响的映射文件和板子都会改变。这种改动要递增 `pad_projection`，并写进编译器的发布说明。
- `designators`：每个需要机器贴装的实例一项，包含：
  - `part` 和 `footprint`（完整路径）；
  - `entry`（`primary` 或替代料的序号），以及该条目的 `mfr` 和 `mpn`；
  - `pn`、`at`（规范 mm 字符串）和 `rotate`。

  没有可用绑定的实例也会列出，写作 `"pn": null`。这表示"明确未绑定"，与"不在这个映射文件里"是两回事。

条目和行的选取方式：

- **可选资格。** 所有输出器画的都是主料的封装，而映射是相对于所在条目自己的封装定义的。所以只有有效封装（条目自己写的 `footprint:`，没写则为主料的封装，与跨 part 身份检查用的规则相同）等于主料封装的条目才有资格被选中。封装不同的已绑定 `alt` 会被跳过；如果因此整组没有可用绑定，E814 会说明原因。它的绑定仍然出现在 API 文档和 registry 中。
- **条目选择按实例进行**，依据该实例所绑定的零件：主料有该 `ID` 的绑定就用主料，否则用声明顺序中第一个有资格且有绑定的 `alt`。
  - 两个零件声明可以有相同的主料 MPN，却允许不同的替代料、料号或映射，现有的身份检查并不要求它们的 AVL 完全相同。如果按普通 BOM 的分组统一选择，就可能违反其中某个声明的约束，所以选择从不在组的层面进行。
  - 套用的映射是**所选条目的映射**，因为替代料在供应商那里的封装可能和主料不同。
- **供应商 BOM 的行**按选定的采购身份合并实例，即（料号, 所选条目的 `mfr`, 所选条目的 `mpn`）。`Comment` 取所选条目的 `mpn`；MPN 来源未给出时留空，此时由 `<ID> Part #` 一栏承担零件的身份。
  - 未绑定的实例改按普通 BOM 的键合并：主料 MPN 和厂商，MPN 为空时再加上所绑定的零件声明。
  - 普通的 `-bom.csv` 保持原有分组方式。
- **映射文件和供应商 CPL 按位号输出**，始终使用该实例自己的选择和映射。
- **未绑定的实例**：料号一栏留空，供应商 CPL 中使用恒等映射，并针对每个未绑定的零件声明报一条 **E814** 警告，指明零件及其位号。只考虑设计实际实例化的零件；声明了但没有使用的零件永远不会产生 E814。它只在给出 `--supplier` 时出现，人类可读输出和 RFC-010 `--json` 输出都会包含。未绑定的零件仍然是正确的设计，所以 E814 永远不会让构建失败。如果设计实例化的所有零件中没有任何条目绑定该 `ID`（通常是 ID 拼错了），逐条警告会被一条 E814 取代：说明这一点，并列出设计中实际绑定了的供应商 ID。
- **排序：** BOM 各行按料号、再按 MPN 排序，位号按自然顺序排列。输出逐字节稳定。

**已布局的板子。** `tools/smt_pos.py` 新增参数 `--map out/<name>-<ID>-map.json`：给了映射文件时，对布局完成的板子上的每个封装按 §2 换算，按中性文件的列写出供应商 CPL，底面行按映射文件中的 `bottom_rotation` 处理（`schema_version: 1` 的映射文件没有这个字段，视为 `kicad`）；不给映射文件、只给 `--neutral` 时，写出中性文件。`--map` 隐含中性列格式。`--all` 不能与 `--neutral` 或 `--map` 同时使用（用法错误，退出码 2）。板子没有外形时，以板坐标原点为原点、y 取反；对 `--emit kicad_pcb` 写出的板子，这正是 §3.1 的源码坐标原点。写出任何文件之前，它先把板子和映射文件对照检查，有问题就不输出：
- **坐标系检查。** 对每个封装，先用和投影相同的筛选规则：只取带编号的焊盘，锡膏开窗和孔因此被排除。然后还原每个焊盘锚点在封装正面局部坐标系中的位置：
  - 减去封装位置，撤销封装朝向，得到板子保存的焊盘相对封装的位置；
  - 在底面再把局部 y 取反。这是 `--emit kicad_pcb` 底面编码的逆变换，也正是 pcbnew 对两种翻面方向翻过的封装的保存方式（翻面方向只影响封装角度）。

  然后把板上焊盘和映射文件的 `pads` 当作**带容差的多重集合**比较：
  - 两边都按焊盘编号分组，每个编号在两边的数量必须相等。
  - 每组内必须存在板上焊盘与映射焊盘的一一配对，使每一对在 x 和 y 上的差都不超过 0.001 mm。任何焊盘不得出现在两对里。
  - 配对不能依赖排序。同编号、x 相同的两个焊盘，可能因为低于容差的舍入误差（x = +0.0000004 对 −0.0000004）而交换顺序，这时把排好序的列表逐项比较，会报出实际上不存在的 2 mm 误差。工具对每组求二分图完美匹配（例如 Hopcroft–Karp，组都很小）。贪心配对不够，因为它也可能拒绝合法的配对。

  零件在板上移动、旋转或翻面都不影响这项检查。封装坐标系变了（例如板上还留着旧版本库的封装）就无法通过；不一致时报错，指明位号和编号最小的失败焊盘组，并按排序列出该组在板上和映射文件中的坐标，保证报错信息确定。用旧版 `pad_projection` 导出的板子也会以同样方式失败，所以报错信息会同时列出这两种可能原因。
- **投影测试。** 一组测试封装覆盖：环形焊盘、分割环形锡膏、矩形和圆形锡膏覆盖、有镀层和无镀层的安装孔、重复的焊盘编号（包括同编号、x 相同、y 不同的两个焊盘）。每个封装都在 `--emit kicad_pcb` 写出的板子上分别放在顶面和底面，各取一个直角和一个非直角旋转。检查必须在这块板子上通过；在 pcbnew 中打开再保存后通过；在 pcbnew 中用两种翻面方向各手动翻一个封装后也通过。把一个焊盘移动 0.01 mm 时必须失败。另有针对匹配算法的单元测试：重复编号的焊盘在 x 上带有正负相反、低于容差的误差；以及旋转 1° 后板坐标按 1 nm 舍入再逆变换。两种情况都必须通过。
- **覆盖检查。** 板上需要贴装的封装如果在 `designators` 中没有对应项，报错"不在这个映射文件里"。`"pn": null` 的项报告为未绑定，按恒等映射输出。映射文件里有、板上却没有的位号报警告。
- 只要有错误，就不写出任何文件。

#### 3.3 其他输出

- `-bom.csv`：不变，逐字节相同。
- KiCad `.net`：对**主料**条目上的每个绑定，在 `MPN`/`MFR` 旁边加一个 `(field (name "<ID 大写>") "<pn>")`，按供应商在源码中的顺序排列。主料没有绑定的实例，输出字节和现在相同。
- `.enet` 网表：仅在给出 `--supplier ID`、且实例有选定条目时：
  - 加上 `Supplier: "<ID 大写>"` 和 `Supplier Part: "<pn>"`。
  - `Manufacturer` 和 `Manufacturer Part` 也取自**同一个选定条目**，避免同一个元件既带主料的厂家身份，又带替代料的供应商料号。现在的 `.enet` 输出器从主料读取这两个字段。
  - 未绑定的实例，以及不带 `--supplier` 的构建，输出不变。
  - 给了多个 `--supplier` 时，用第一个。
  - 加一个只有替代料绑定的测试（即 §1 中的 C_100n_16V_X7R_0402 示例），确认 BOM、映射文件和 `.enet` 用的是同一个选定条目。
- API 文档（`cohdl docs`）：每个 AVL 条目新增一个 `suppliers` 数组，内容为 `[{ supplier, pn, at: [x, y], rotate }]`，坐标为规范 mm 字符串，按声明顺序排列。每个键总是出现，缺省值也写出（`["0mm", "0mm"]`、`0`）。`schema_version` 不升级：这个键对版本 1 和版本 2（RFC-033 的格式）都是纯新增，现有字段不变。

### 4. Registry

**供应商表。** 新建 D1 表 `suppliers`（迁移 `0005`），每个已知供应商 ID 一行，内容包括：
- 显示名称；
- 带 `{pn}` 占位符的商品页链接模板，例如 `https://parts.example.com/{pn}`；
- 该供应商目录所用的分类体系（如有）。

由官方账号维护。绑定到未登记供应商的料号照常显示，只是没有链接。

**厂商别名。** 同一迁移新增 `manufacturer_aliases` 表，把别名映射到规范的厂商名，由官方账号通过管理 API 维护。§5 比较厂商名时，先做 Unicode 大小写折叠、把连续空白合并为一个，再把两边都经此表映射。归一化和别名映射都在 registry 里完成，所有客户端比较的是同一套 key（见下文）。

**目录表。** 新建表 `supplier_catalog`，以 `(supplier, pn)` 为键。字段有 `mpn`、`manufacturer`、`package`、`class`、`stock`、额外的 `links`（标签 + 链接，用于无法从模板推导出的供应商页面）和 `fetched_at`。
- 按供应商整体替换，数据来自通过管理端接口上传的快照。Worker 不访问供应商网站。
- 快照包含什么、如何采集，不在本 RFC 范围内。

**索引。** `registry/src/worker/search.ts` 把 API 文档中的 `suppliers` 数组读入零件索引，与 `mfr`/`mpn` 并列，并和其他投影一样设上限（新增 `MAX_SUPPLIERS_PER_AVL = 16`，与 `MAX_AVL_ENTRIES_PER_PART` 并列）。料号也加入可搜索文本，所以搜料号就能找到对应零件。

**对外接口**（全部为新增；和 `/search` 一样只读、无需登录）：

- `GET /search` 的零件结果新增 `suppliers: [{ supplier, pn, at, rotate, links, catalog|null }]`。
  - `catalog` 包含 `class`、`stock` 和快照日期。
  - 新增可选参数：`supplier=ID`，以及 `class=…`（可重复，必须同时带 `supplier`）。
  - 零件匹配的条件是：它有该供应商的绑定，且该绑定的目录行属于所列分类之一。不带这些参数时，结果不变。
- 新增 `GET /suppliers/{id}/parts`，有两种形式（每次请求最多 100 个值；每个响应都带快照日期）：
  - `?pn=P1,P2,…`：返回每个料号的目录行，或 `unknown`。
  - `?mpn=M1,M2,…`：对每个 MPN，返回归一化（大小写和空白）后 MPN 相同的目录行。排序依次为：分类顺序（按供应商表中声明的顺序）、是否有货、库存多少。
  - 每个目录行还带 `mpn_key` 和 `manufacturer_key`：归一化后的 MPN，以及经别名映射后再归一化的厂商名。
  - 查询值按原样匹配。同一个值可以重复出现，每次出现都按输入顺序各自返回结果。料号按原样精确查找，没去首尾空白或不是 NFC 形式的料号直接返回 `unknown`。空值、控制字符、超过 256 字节的值、超过 100 个值会被拒绝。列表以逗号分隔，所以含 `,` 的值无法查询。
- 新增 `GET /manufacturers/normalize?mfr=…&mpn=…`（两个参数都可重复，各最多 100 个，取值规则同上）：按输入顺序返回 registry 对每个值算出的 key。客户端从不自己归一化名称。
- `cohdl search` 显示绑定，新增 `--supplier ID` 和 `--class C`（可重复），`--json` 原样带出 `suppliers`。
- registry 网页的零件页面列出每个供应商及其料号、映射、链接、分类和快照日期；搜索页提供按供应商和分类的筛选。

### 5. `cohdl suppliers`：在线核对与推荐

`cohdl suppliers <dir> [--supplier ID]... [--json]` 先像 `check` 一样离线解析项目，再查询 registry。项目未通过 `check` 时，和 `check` 一样以退出码 1 结束，不发任何查询。

- **对每个绑定**（可限定为指定供应商），报告以下状态之一：
  - `ok`
  - `unknown`：料号不在该供应商的快照中
  - `mismatch`：归一化后，目录中的 MPN 或厂商与条目不一致；厂商名称通过 registry 维护的别名表比对。来源未给出（留空）的字段不参与比对，所以不会导致 `mismatch`；报告把目录里该字段的值仅作参考展示，绝不建议把它写进源码。
  - `out-of-stock`（缺货）
- **对指定供应商下没有绑定的 AVL 条目**，报告 `unbound` 并给出**推荐**：该供应商目录中与条目 `mpn` 匹配的行，排序方式同 `/suppliers/{id}/parts?mpn=`。`mpn` 为空的条目没有可匹配的内容，报告为 `unbound` 且不给推荐。
  - 每条推荐显示料号、分类、库存、目录中的厂商，以及该厂商是否与条目的 `mfr` 一致。厂商一致的推荐排在前面。
  - 推荐中绝不包含映射：registry 无法知道供应商的封装相对设计的封装是怎样摆放的。
  - 该命令从不修改源码。`--json` 以结构化数据给出推荐，供修复流程使用。
- **范围。** 和 E814 一样，核对设计实际实例化的零件的全部 AVL 条目（主料和替代料）。不给 `--supplier` 时，核对这些条目绑定的所有供应商 ID，不报 `unbound`。
- **比较**使用 registry 算出的 key（§4）：目录行的 `mpn_key`/`manufacturer_key`，对比 `/manufacturers/normalize` 为条目的 `mpn` 和 `mfr` 返回的 key。
- **无法向 registry 查询的值。** 料号含 `,` 或超过 256 字节时，不发查询，直接报 `unknown` 并注明原因。这样的 `mpn` 报 `unbound` 且不给推荐。超过 256 字节的 `mfr` 或 `mpn` 不参与比较，和留空一样处理。
- **未登记的供应商。** registry 没有某个供应商 ID 的目录（`404 supplier not found`）时，报告在供应商一级说明这一点，不逐条列出它的绑定状态。这不影响退出码，因为 §4 允许绑定到未登记的供应商。
- **退出码：**
  - 所有被核对的绑定都是 `ok` 时为 0
  - 任一为 `unknown` 或 `mismatch` 时为 3
  - registry 或协议故障时为 1（E1204）
  - 参数无效时为 2
  - `out-of-stock` 和 `unbound` 只报告，不影响退出码。
  - 退出码 3 是命令行新增的（现有命令只用 0/1/2），要写进 `cohdl --help` 和命令行退出码文档，其他命令不使用它。
- **它永远不在 `check` 或 `build` 中运行。** 相同的源码和锁文件必须得到相同的判定结果和输出字节，每天都在变的事实不能进入其中。需要这道关卡的 CI，单独加一步运行 `cohdl suppliers`。
- `--json` 是它自己的报告格式，和 `cohdl search --json` 一样，不是 RFC-010 诊断格式。

## 类型系统优先检验

不适用：本 RFC 不提出任何 `rule`/DRC 检查。所有编译器检查都是在 AVL 条目上做的声明时合法性检查（E813），或复用单位检查。

## 概念影响

不新增声明种类。**供应商绑定**是现有 AVL 条目的一个新属性：供应商 ID、料号和贴片映射。它把 Part 概念的采购身份从"谁生产"（`mfr`、`mpn`）扩展到"谁销售或贴装它，以及怎么贴"。

用词：
- "供应商"（Supplier）和"供应商料号"（supplier part number）是新术语，与现有术语不重叠。
- 避免使用 "Source"，因为在 CoHDL 里它处处指源代码和源文档。
- `at`/`rotate` 保留它们作为放置变换的原有含义，这里用于两个封装坐标系之间。

## 一致性矩阵

| 概念 | 语法 | 判定 | 诊断 | 网表 | 兼容性 | 可信度 |
|---|---|---|---|---|---|---|
| 低 | 中 | 中 | 低 | 中 | 低 | 中 |

- **语法（中）：** AVL 条目内新增一种项的写法，由现有部件组成（一个标识符、一个字符串、现有的 `at`/`rotate` 子句），按上下文识别。不新增保留字；`fmt` 新增一种规范写法。
- **判定（中）：** 编译器能验证结构和单位，但无法验证料号是否真的对应那个 MPN，也无法验证映射是否正确。应对方式：
  - `cohdl suppliers`（联网运行，不影响判定结果）；
  - registry 中带日期的目录状态；
  - 对官方库，由库计划里的库 CI 和贴片厂预览把关。
- **网表（中）：** 只有主料带绑定的实例，`.net` 字节才会变化。中性 CPL 是新文件，只为有放置信息的设计写出。供应商输出和 `.enet` 的供应商属性只在给出 `--supplier` 时出现。所有现有输出文件的字节都不变。
- **可信度（中）：** 料号和映射是作者的声明，和现在的 MPN 一样。每天变化的信息都留在 registry 里，并标注日期。

| 事实 | 检查方式 | 阶段 |

| 供应商 BOM 是否完整 | 每个未绑定的零件声明一条 E814；ID 在设计中无任何绑定时只报一条 | build，仅在给出 `--supplier` 时 |

## 可被 AI 生成

子句只作用于它所在的条目，读起来像一次放置。供应商名是自由文本，所以模型绑定任何供应商都不需要特殊处理。

主要有两个风险，各有应对：
- **编造料号。** `cohdl search --supplier` 返回真实料号；`cohdl suppliers` 把错误的料号变成明确的 `unknown`/`mismatch` 行，并为未绑定的条目给出排好序的推荐。
- **编造映射。** 映射默认为 (0, 0, 0°)；文档要求只有依据供应商的封装才写非零映射；推荐中也从不给出映射。

## 备选方案

1. **每个供应商一个平铺的键**（`acme: "A-104411"`）。这是上一版草案。否决：它无法携带映射，而且每加一个供应商，编译器的键集合就要变大。
2. **封装级默认映射**（`footprint F { supplier acme rotate 180 }`）。推迟：映射取决于具体料号在供应商那里的封装，封装族级的默认值可能被悄悄套用到不适用的零件上。以后可以作为默认值加入，由逐条目的子句覆盖。
3. **只在 registry 里存绑定。** 否决：输出将无法离线复现，本地包也无法使用，而且 registry 会凌驾于不可变的包内容之上。
4. **每个包一个附加数据文件。** 否决：它会成为 AVL 之外的第二个事实来源，无法表达逐个 `alt` 的绑定，也无法在编译时检查。
5. **编译器内置封闭的供应商列表并做格式检查。** 否决：这会把供应商知识写进语言，每新增一个供应商都要发布新编译器。格式检查应放在 registry 的供应商表和 `cohdl suppliers` 中。
6. **只有旋转，没有偏移。** 否决：供应商封装的原点常常不在本体中心（连接器、模块），而 CPL 的位置错误和旋转错误一样有害。
7. **CPL 只在请求时输出（`--emit cpl`）。** 好处是不新增默认文件，而且能自动继承 `--emit` 与 `--logical-only` 的互斥。未采用：对有放置信息的设计来说，CPL 和 BOM 一样是最基本的组装输出，板子作者也要求默认输出。代价改用其他方式控制：只有含放置信息的设计才写这个文件，部分放置的设计只报一条汇总的 E815，`--logical-only` 明确不写它（§3）。
8. **用焊盘质心作为位置**（`smt_pos.py` 现在的 `Mid X/Y`）。中性文件不采用：焊盘重画时质心会移动，而 §2 的映射定义在两个封装原点之间。脚本现有的输出对现有用户仍保留质心。
9. **把底面约定作为供应商声明写进语言**（`supplier acme { bottom_rotation: mirrored }`，2026-10-29 的一版修订）。不采用：它为一项关于导出目标的事实新增了一种声明形式和两条诊断，而且同一份设计会随所构建的包集合不同而改变含义。用构建参数可以保持语言不变，源码只有一种约定。

## 兼容性

- **语言：** 纯新增。所有现有 `.cohdl` 文件含义不变。新增 E813（错误）、E814 和 E815（警告），编号为临时编号。
- **输出：**
  - BOM CSV：不变。
  - `.net`：只有主料带绑定时才变化。
  - `.enet`：只有给出 `--supplier` 时才变化。
  - `-cpl.csv`：新的默认输出，只在对含有 `place` 的设计做物理构建时写出；所有现有输出文件的字节不变。`--logical-only` 构建写出的文件与现在完全相同。
  - `tools/smt_pos.py`：默认输出不变；`--neutral` 和 `--map` 为新增。
  - `build --json`：新增 `cpl` 和 `suppliers` 键。
  - `-<ID>-bom.csv`、`-<ID>-map.json`、`-<ID>-cpl.csv`：新增，仅在给出 `--supplier` 时输出（CPL 只在物理构建中输出）。
  - API 文档：新增字段。
- **Registry 和命令行：** 纯新增（零件结果中的 `suppliers`、`supplier=`/`class=` 筛选、`/suppliers/{id}/parts`、`cohdl suppliers`）。
- **库：** 本 RFC 不要求库做任何改动。

## 工具与运维

- **通过后需要更新的文档：**
  - 第 10 篇（语言规范）：供应商子句和映射规则。
  - `docs/provisional-syntax.md` §2：AVL 条目的项列表。
  - `docs/error-codes.md`：E813、E814、E815。
  - `cohdl build --help`：`--bottom-rotation`。
  - `docs/apidocs.md`：`suppliers` 数组。
  - `.enet` 网表、BOM 和 CPL 输出的相关文档。
  - `tools/smt_pos.py` 的文档：`--neutral`、`--map`。
  - `cohdl --help` 和命令行退出码文档：`cohdl suppliers` 的退出码 3。
- **`fmt`：** 规范写法为 `supplier ID "PN" at (Xmm, Ymm) rotate N`。写了的 `at`/`rotate` 保留，没写的不补。供应商子句总是排在所有 `name:` 字段和 `footprint` 之后（这些项保持现在按源码位置排序的方式），供应商子句之间保持源码顺序；写在前面的子句会被 `fmt` 移到后面。
- **LSP：** 在 AVL 条目内提供 `supplier` 补全；缓存了 registry 供应商表时，悬停显示供应商显示名称和链接。
- **`check --json` / `build --json`：** E813/E814/E815 作为普通诊断输出，RFC-010 的格式不变。
- **零依赖规则：** 不受影响。编译器的改动只有解析、检查、字符串输出和定点数变换；所有联网访问都在 registry 和 `tools/` 中。

## 学习成本

- **作者**只需学一个子句：供应商、料号，以及描述供应商封装相对我们封装位置的可选 `at`/`rotate`。
- **审阅者**需要知道供应商 BOM 和坐标文件用哪个条目：按实例，主料有绑定就用主料，否则用第一个与主料封装相同且有绑定的 `alt`。还需要知道中性 CPL 不含任何映射。
- **工具开发者**需要掌握 §2 的组合规则。

## 失效模式

- **料号写错。** E813 捕获结构错误；`cohdl suppliers` 捕获不存在或不匹配的料号。
- **映射符号或方向写反**（写成从供应商到我们的变换）。CPL 会转错或偏移。§2 固定了唯一的方向，文档会给出完整示例；贴片厂的贴片预览是最后一道检查。
- **两个零件主料相同，但允许的替代料不同。** 已处理：按实例、依据其自己的零件选择条目（§3.2），供应商 BOM 只合并选定身份完全相同的实例。
- **映射文件被套用到封装坐标系已过时的板子上。** 例如库移动了某个封装（破坏性发布），映射文件也重新生成了，但已布线的板子上还是旧封装。坐标系检查会失败并指明位号和焊盘，不会写出 CPL。
- **板子是用旧版焊盘投影导出的。** 封装坐标系没变，但锚点移动了，例如环形焊盘锚点的规则改过。坐标系检查会失败而不是去猜；报错信息同时列出两种可能原因，重新导出板上的封装即可解决。
- **替代料有自己的封装。** 所有输出器画的都是主料的封装，所以有效封装不同的替代料不会被选进供应商输出（§3.2），否则它的映射描述的会是板上并不存在的铜皮。在有资格的条目中，映射文件和供应商坐标文件携带的是所选条目的映射，绝不默认使用主料的映射。
- **底面角度约定。** 不同贴片厂读取底面旋转的方式不同。中性 CPL 固定了一种约定（KiCad 的，见 §3.1），并由一致性测试对照板子固定下来。某个贴片厂是否需要别的约定属于供应商知识，由它的贴片预览确认，再由为该贴片厂导出的人用 `--bottom-rotation`（§3.2）指定；编译器按参数执行，但不认识任何具体的供应商。忘了给参数时得到 KiCad 的约定，构建输出会在每个供应商 CPL 旁注明。
- **过期的供应商文件。** 由归属清单处理：之前用 `--supplier` 生成、这次不再生成的文件会被删除（§3）。
- **供应商 ID 拼错。** 只报一条 E814，说明该 ID 在设计中没有任何绑定，并列出实际绑定了的 ID。
- **把中性 CPL 交给了坐标系不同的供应商。** 零件会贴转或贴偏。中性文件的文件名里不带供应商 ID；只要给出 `--supplier`，供应商坐标文件就会与它并排输出。
- **零件在 CoHDL 之外放置。** 编译器输出的 CPL 只包含源码中放置过的实例，其余的由 E815 列出。在别处布局的板子，坐标文件由 `tools/smt_pos.py` 生成。
- **MPN 未知的零件。** 来源未给出 MPN 的条目上，供应商料号是作者唯一的下单依据，离线无法核对。`cohdl suppliers` 能报告该料号是否存在，但不会因留空的字段报 `mismatch`；BOM 行的 `Comment` 保持为空，不借用目录里的 MPN。
- **指望逻辑构建产出 CPL。** `--logical-only` 按设计不写 CPL；未通过物理导出检查的物理构建也不写。两者都不会写出残缺的文件。
- **底面贴装的零件。** 映射走现有的"先镜像再旋转"组合，测试会把顶面和底面两种情况都对照几何输出器固定下来。
- **供应商更改或停用料号。** registry 显示为 `unknown`，`cohdl suppliers` 退出码为 3。在发布新版本之前，包里保留原绑定。

## 待定问题

- **映射是否需要镜像。** 映射是刚体变换（偏移加旋转），无法表达与我们的封装互为镜像的供应商封装。目前已知唯一的反装件（一款已在量产中验证的侧发光 LED）只需要旋转，所以在出现真实需求之前不加入镜像。
- **底面约定的实际效果（2026-10-29 已解决）。** §3.1 采用 KiCad 的约定，这是从 `--emit kicad_pcb` 写底面角度的方式推出来的。测试板上放了四种零件，分别位于顶面 0°、顶面 37°、底面 0° 和底面 37°。在这块板上，`tools/smt_pos.py --neutral`、编译器 CPL 和 KiCad 自己导出的坐标三者一致。某一家贴片厂的预览把所有位置和面别都贴对了，但它把底面角度读作 `(180 − θ) mod 360`：三轮预览中，底面零件只在 90° 和 270° 时与它一致，37° 的几份偏了 74°，套用这个换算后才对齐。这一约定在导出时由 `--bottom-rotation ID=mirrored`（§3.2）承载，语言和中性文件保持 KiCad 的约定。

## 迁移路径

无需迁移。设计可以给自己的零件加上子句来使用供应商输出，也可以更新到带有绑定的库版本。

## 决定

草案，2026-10-23；2026-10-27 和 2026-10-28 根据四轮对 `329af05` 源码的审查修订（第三轮定义了映射文件的焊盘投影，第四轮定义了它的匹配规则）。待评审，尚无决策记录。

正式通过之前可以分阶段实现：
- 子句语法、检查、`fmt`、逐实例选料、供应商 BOM、registry 和 API 文档不依赖映射文件的检查，现在即可开始。
- 映射文件、两种 CPL 和 `smt_pos.py` 的新参数按本版的焊盘投影规则实现。
- 官方库的绑定和封装对齐，只有在对应料号已确认、并具备坐标系证据时才能发布（按库计划的规则）。

实现状态（2026-10-28）：所有阶段都已在本地分支 `feat/rfc-034` 上实现，编译器、registry 和工具的测试全部通过。实现过程中做出的裁决已并入上文 §1、§4、§5。有两项投影测试需要 pcbnew，以人工检查清单的形式保留（打开再保存，以及两个方向各手工翻面一次），属于正式通过的条件。LSP 的补全和离线悬停已实现；悬停时显示 registry 中供应商的显示名和链接，要等本地有供应商表缓存后再做。

2026-10-29 修订：新增 `--bottom-rotation` 和映射文件中的 `bottom_rotation`（§3.2），依据是"待定问题"中的贴片厂预览。同日较早的一版把这一约定作为供应商声明写进语言，已撤回（见"备选方案"第 9 条）。pcbnew 检查清单已在 KiCad 10.0.7 上完成：用 pcbnew 和 `kicad-cli` 分别打开再保存；顶面和底面零件在直角和 37° 下各沿两个方向翻面；焊盘移动 0.01 mm。19 种情况的结果全部符合规定。

正式通过仍需两项：在中央登记分配 RFC 编号和错误码；在编译器依据 `--bottom-rotation` 处理底面约定之后，重做一次贴片厂预览验证。在此之前，本文不视为冻结。本文件是仓库快照里的工作副本，正式 RFC 应放在 conol.ai 设计库中，由那里分配编号和错误码。

Same bytes, every time

CoHDL promises that compiling the same source with the same dependencies produces the same output — not equivalent output, the same bytes. This post is about what that promise costs, why hardware demands it anyway, and the day sine and cosine nearly broke it.

Tony Huang · August 17, 2026

The promise, stated exactly

CoHDL's constitution has one hard constraint that outranks everything else: same source plus the same exact dependency set produces the same verdict, the same designators, and the same output bytes. Not "equivalent" output. Not output a sufficiently clever diff tool would accept as the same design. The same bytes, byte for byte, on every machine, forever — for everything the compiler emits: the KiCad netlist, the BOM, the layout.json constraint document, every generated footprint, the IPC-2581 handoff file, the physics-hint CSVs, the lock files.

This is checkable, so let me check it. Here is the compiler's own Raspberry Pi Pico 2 example — a CoHDL transcription of the RP2350A board from its datasheet — built on my machine, with the four main outputs hashed: 

$ cohdl build rpi-pico2 --emit ipc2581
$ cd rpi-pico2
$ shasum -a 256 out/rpi-pico2.net out/rpi-pico2-bom.csv \
    out/rpi-pico2-layout.json out/rpi-pico2.xml

Delete out/, build again, hash again: the same four lines. That is not a benchmark result that holds on average. It is an invariant the compiler is engineered around, and this post is about what it takes to keep it true.

Hardware does not forgive drift

For most software, "the build is reproducible" is hygiene. For hardware it is closer to a safety property, for three reasons.

First, a board rebuilt in a year must be the board you validated. You brought up a physical object, probed it, shipped it. The netlist and BOM that produced it are the record of what you validated. If regenerating them from the same source produces different bytes — reordered nets, renumbered designators, a coordinate off in the last digit — you can no longer prove the artifact in front of the fab is the artifact you tested. You can only believe it.

Second, a diff in generated output must mean the design changed. CoHDL designs check their compiler outputs into version control, so every schematic edit shows up twice in review: the source diff and the consequence diff in the netlist and BOM. That second diff is only worth reading if it is guaranteed to be signal. The moment output can wobble for reasons unrelated to the design — a different machine, a different iteration order, a different libm — reviewers learn to skim generated diffs, and then the one diff that mattered goes by unread.

Third, content hashes only work if output is a pure function of input. CoHDL's cohdl.lock records the exact version and the sha256 content hash of every dependency, and re-verifies those hashes on every check and build before parsing a single line; the package registry records the hash of each published archive and the client refuses anything that does not match. A hash is a strong statement — these exact bytes and no others — and it is only worth making about a package's contents if those contents are themselves deterministic all the way down.

What the promise costs

Byte-stability is not a feature you add. It is a discipline you keep, everywhere, forever. Three of its prices are worth naming.

The pipeline has zero external dependencies. Every format the compiler reads or writes is hand-rolled: the TOML of the lock files, the S-expression netlist, the JSON diagnostics and layout.json, the IPC-2581 XML, the CSVs. This is not dependency-phobia. A third-party serializer is a third party's opinion about byte layout, and a patch release that reorders keys or reformats floats would change our output without any change to any design. The one scoped exception is the LSP layer, which borrows the protocol's message types — and sits nowhere near the output path.

No hash-map iteration order gets anywhere near output. Rust's HashMap deliberately randomizes iteration order per process, which makes it a determinism leak with excellent camouflage: correct output, every run, in a different order each time. Everything output-adjacent in the compiler is a BTreeMap or an explicitly sorted vector, as a rule with no exceptions rather than a preference.

Designators are allocated by a pure function, and the compiler checks its own work. The v1 compiler allocated reference designators the obvious way — walk the instances, keep a mutable set of used names, take the lowest free number — and the obvious way produced a real bug: two parts in a real design both landed on U3. A stateful loop is the wrong shape for something a BOM depends on, so v2's allocator (RFC-005) is a pure function: for each prefix, the full reserved-number set — prior assignments, tombstones, explicit overrides — is computed once, immutably, before any fresh number is chosen; new instances, sorted by hierarchical path, then take the missing integers in order. Two instances cannot collide because they are not searching; they are reading different positions from one precomputed sequence. And because "provable by construction" is still a claim about code humans wrote, the allocator asserts injectivity — no two instances share a designator — as an explicit postcondition on every single run.

Stability across edits comes from design.lock: an instance that already has a designator keeps it no matter how the source is reordered, and a deleted instance leaves a tombstone so its designator is never reissued.

The tombstone table is the quiet one, but it earns its place. If deleting a capacitor lets a future part inherit C2, then every old assembly drawing, rework instruction and bring-up note that mentions C2 now points at the wrong component. A designator is a name that escaped into the physical world; it must never mean two things.

The day sine and cosine became a problem

For most of its life the compiler rotated parts without trigonometry. Placement rotation was a closed set — 0, 90, 180, 270 — and rotating a pad offset by a quarter turn is an exact integer swap: rotate (x, y) by 90 and you get (-y, x), no rounding, no error term, nothing to be nondeterministic about.

Then real boards wanted real angles, and rotate now accepts any whole degree from 0 to 359 — rotate 37 compiles as happily as rotate 90. Which means the compiler suddenly needs the sine of 37 degrees, and the obvious way to get it is f64::sin. It compiles, the tests pass, the coordinates look right — and it quietly breaks the promise this post is about. f64::sin resolves to the platform's math library, and the last bit of libm's result is not guaranteed identical across macOS, glibc and musl. A rotated pad coordinate is emitted geometry, so a one-bit disagreement between two machines is two different artifacts from the same source. The build machine would leak into the netlist, and a registry hash would depend on which operating system happened to publish the package.

So the compiler does not compute sines. It looks them up. The sine of every whole degree from 0 to 90 is a checked-in integer constant, scaled by 264, generated once by a small script; the other three quadrants come from symmetry, and every rotation is integer arithmetic over those constants:

The details are all load-bearing. The scale is 264 rather than a power of ten so that reducing a product back down is a bit shift, never a 256-by-128-bit division. Tabulating only the first quadrant and deriving the rest by symmetry keeps the four cardinal angles exact — sin 90° is exactly 264, cos 90° exactly zero — so the table path agrees with the old exact-swap code to the bit, and every board authored before arbitrary angles existed still emits identical bytes; a regression test holds both example boards to that. Coordinates are integers on a femtometre grid, and at the outer bound of the accepted geometry range a coordinate times a 264-scaled constant needs 164 bits, so the multiply runs through a 256-bit intermediate instead of shrinking either the coordinate range or the table's precision. The module's own doc comment states the standard the whole compiler is held to: deterministic by construction, not by luck.

Determinism is the trust interface

It would be fair to ask whether all this is pedantry — whether "semantically identical" output would not serve just as well. I think byte-stability is the more honest engineering target, because it is the one you can verify without trusting anyone, including us. "Equivalent" requires a judge; "identical" requires diff.

That matters more, not less, as models write a growing share of schematics. You cannot review a model's intentions; you can only review its artifacts, and byte-stable compilation is what makes the artifacts reviewable. The source is the design, the outputs are a pure function of it, and every tool that made software auditable comes along for free: git history that means something, CI that treats a netlist diff as a design-review event, a registry that can hash-verify every dependency of every build, a fab package you can reproduce from source years later and prove it.

Same bytes, every time is not a performance claim and it is not polish. It is the property that lets text tooling — version control, diff, code review — govern physical hardware. Everything else in CoHDL stands on it.

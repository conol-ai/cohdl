# 官方库供应商计划（LCSC / 嘉立创）

> 中文版，以英文版 [`library-supplier-plan.md`](library-supplier-plan.md) 为准。

状态：计划，2026-10-23；2026-10-27 对照 main `329af05` 修订。这是库建设工作，不是语言设计。它使用 [RFC-034](design/rfc-034-supplier-binding.md) 定义的供应商绑定，并遵循 [`LIBRARY.md`](../LIBRARY.md) 的编写规则。本计划为官方库新增的规则，会在对应工作线落地时并入 `LIBRARY.md`。工作项、先后顺序和验收方法见[实施计划](library-supplier-impl-plan.zh-CN.md)。

## 目标

官方库以嘉立创贴片和立创商城（LCSC）采购为基准。本计划完成后：

1. **都有料号。** 立创有货的每个官方零件，都在负责下单的那个 AVL 条目上写好 `supplier lcsc "<C 编号>"`。
2. **都已对齐。** 每个官方封装都和嘉立创的贴片坐标系对齐，因此官方库里所有 `lcsc` 映射都是 `(0, 0, 0°)`，子句不需要写 `at`/`rotate`。唯一的非零映射是登记在案的例外（见 W3）。
3. **覆盖常用料。** 库覆盖嘉立创的 Basic 和 Preferred 清单（2026-10-06 共 1586 个，当时已覆盖 20 个），扩展库的料按需补充。
4. **可直接上传。** 用官方零件做的设计能生成 LCSC 的 BOM，并通过 `tools/smt_pos.py --map` 生成坐标文件（CPL），嘉立创直接接受，不需要手工对料，也不需要修正旋转。

焊盘编号、焊盘几何和引脚映射仍以厂商文档为准。对齐只移动整个封装，绝不修改任何一个焊盘。

## 基本规则

- **任何工具都不从 EasyEDA 获取数据。**（这和编译器的 `--emit easyeda` 网表输出无关：它只是写出一个供 EasyEDA/立创 EDA 专业版导入的文件，不访问任何网站。）EasyEDA 的条款（2026-09-21 生效）限制批量或系统性的自动访问，并限制对其内容的衍生使用；具体内容另有适用许可的除外（开源内容沿用其自身许可）。本项目的规则比条款更严：任何工具都完全不从 EasyEDA 抓取。它的封装也不能当权威：焊盘尺寸和厂商推荐值差 0.1–0.35 mm，SK6812MINI-E 画的是正贴版本。遇到问题时可以由人手工查看供应商的封装来判断，但不复制任何内容。
- **不请求 robots.txt 禁止的路径。** 对嘉立创来说，就是 `/api`。
- **所有工具共用一个 HTTP 客户端，遵守同一套抓取规范：**
  - 每个站点每 2 秒最多 1 个请求，每次运行设请求总数上限。
  - 按 URL 缓存；输出为带日期的快照。
  - User-Agent 为 `cohdl-library-bot/<v> (+https://github.com/conol-ai/cohdl)`。
  - 遇到 403/429 先退避；连续两次就停止本次运行。不换 IP，不用代理。
  - 只保存事实字段（C 编号、MPN、品牌、封装名、分类、库存、datasheet 链接、商品页路径），绝不再分发原始页面。
- **拿不准就停下。** 工具无法判断时（匹配有歧义、厂商冲突、缺少证据），把情况写入待人工复核清单，不做任何改动。

### W1：料号清单快照

`tools/jlc_catalog.py` 维护一份 Basic/Preferred 清单的快照，带日期和哈希。每一行包含：C 编号、MPN、品牌、封装、分类、库存、datasheet 链接，以及取自 sitemap 的完整 `partdetail` 路径。工具从不依赖 `partdetail/C<n>` 这种短链接。之前的草稿举例说短链接会显示错误的料，但 2026-10-27 未能复现，所以这条规则的依据是"使用规范路径"，而不是那个例子。

- **基线：** 2026-10-06 统计到 351 个 Basic、1235 个 Preferred，但原始数据只存在会话临时目录里，没有保留下来。因此第一份提交的快照要重新生成：从下面的来源取候选，每个都在 `partdetail` 页面上确认，提交时附上来源清单、日期和哈希。
- **每季度刷新（自动）：** 逐个重新读取快照中每个 C 编号的 `partdetail` 页面。这些页面 robots 允许，服务端直接渲染分类信息。升级、降级和库存变化写入一份带日期的差异记录。按每 2 秒一个请求，1586 个料的请求预算约为 53 分钟；实际耗时（含传输和重试）随每份快照记录。
- **每季度发现新料（人工辅助）：** 新进入 Basic/Preferred 的料，无法从服务端渲染的页面里枚举出来，因为列表页第一页之后的内容都通过 `/api` 加载。
  - 由维护者在自己的浏览器里翻阅 jlcpcb.com 的 Basic 和 Preferred 筛选页（约 32 页），用 `tools/` 中提供的页面复制小工具导出页面上显示的 C 编号。
  - 新编号经刷新流程在各自的 `partdetail` 页面核实后，才进入快照。
- **官方清单：** 向嘉立创（客户经理或 support@jlcpcb.com）索要 Basic/Preferred 清单。如果拿到了，或者获批了 Components API，就用它替代人工发现。
- **jlcparts 作为候选来源（2026-10-27 重新评估）。** 它当前的快照（2026-10-27 生成，`data/manifest.json`）有 354,819 个零件，其中 235,266 个编号低于 C6374508，所以 2026-10-06 得出的"没有 C6374508 以下的料"已不成立。每条记录都带分类（`Basic`、`Preferred` 或 `Extended`）。2026-10-27 对全部 1089 个元件分片做了完整统计，结果是 **350 个 Basic、984 个 Preferred**；2026-10-06 在网站上数到的是 351 和 1235。也就是说，jlcparts 的 Basic 几乎完整，Preferred 不全。原因尚未查明：一是两次统计日期不同，二是它可能只收录了部分零件。因此它只作为重新生成基线和 W2 的**候选来源**，不能直接当作目录本身：每个候选都要在 `partdetail` 页面上确认，缺口由人工辅助发现来补。
- **已保存的候选起点：** 1,334 对 C 编号和 MPN（350 个 Basic、984 个 Preferred）已存入 [`basic_preferred.json`](../tools/sourcing_data/jlcparts/2026-10-27/basic_preferred.json)，同时保存了原始[运行日志](../tools/sourcing_data/jlcparts/2026-10-27/run.log)和[来源、数量及 SHA-256 哈希](../tools/sourcing_data/jlcparts/2026-10-27/provenance.json)。它是重建 W1 的输入，仍需逐个在 `partdetail` 页面上确认，不是已核实的目录基线。
- **完整的 `partdetail` 路径：** 嘉立创的 parts sitemap 在 robots.txt 中声明为 `https://jlcpcb.com/sitemap-index.xml`，共 146 个文件，每个最多 50,000 条链接，所以最多约 730 万条链接。这个数不等于零件数。2026-10-27 抽查第 1 和第 146 个文件，发现：
  - 非详情页链接：第 1 个文件里有 2,547 条分类页；
  - 一条占位链接 `…/C0/C0`；
  - 第 146 个文件的 38,993 条详情链接中，有 11,210 条用的是 10 位数的 `C99…` 编号，链接前缀常常为空。这些是不是 LCSC 料号，尚未确认。

  因此导入时：只保留两个 C 编号相同且非零的 `partdetail/<片段>/<C>/<C>` 链接；10 位数编号在核实前单独归类；按 C 编号去重；报告过滤后的总数。只有出现在过滤后集合里的 C 编号，才能通过 sitemap 查到。身份（料号、MPN、厂家）一律在 `partdetail` 页面上确认。sitemap 里没有分类信息，所以不能替代人工发现新料。
- **不能作为数据源（2026-10-22 核查）：**
  - jlcsearch：分类筛选和分页参数无效。
  - ole00 的 `basic_parts.csv`：2023 年的旧数据，GPL-2.0 许可。
  - jlcparts 的衍生数据（CDFER、kicad-jlcpcb-tools）在 jlcparts 改格式之后没有重新评估，不使用。

### W2：给现有零件回填料号

`tools/lcsc_backfill.py` 为每个官方 AVL 条目查找对应的立创 C 编号。

- **规模（按 `329af05` 重新统计）：** 共 21,018 个不同的 MPN（`lib/passive` 里 17,431 个，其他 3,587 个）。
- **查询入口（2026-10-27 核查）。** 按自定的抓取规则，没法逐个 MPN 去供应商网站搜索：
  - 嘉立创的搜索走 `/api`。
  - 立创商城的 `/search?q=` 虽然 robots 允许，但在浏览器端渲染，服务端返回的 HTML 里没有结果。
  - 立创商城的 sitemap 只有 C 编号（`product-detail/C….html`），约 790 万条。

  所以回填改从嘉立创的 parts sitemap 入手：
  1. **建索引。** 每次运行先把 146 个 sitemap 文件下载一遍（约 1 GB；按每 2 秒一个请求，请求预算约 5 分钟，实际耗时另行记录），按 W1 的规则过滤，并把 jlcparts 的记录作为第二个候选来源，离线建立"归一化 MPN → （C 编号，完整 `partdetail` 路径）"的索引。链接里的 MPN 会丢信息：标点会变成 `_` 或被去掉（例如 `MP1482DS-LF-Z` → `MP1482DS_LFZ`），前缀有时是厂家名，有时只是数字。所以两边都只保留大写字母和数字再比较，命中的结果都只是**候选**。
  2. **确认。** 逐个打开候选的 `partdetail` 页面（robots 允许、服务端渲染），读取准确的 MPN、厂家和分类。一个 MPN 有多个候选时，每个都要打开。所以请求预算至少是每个匹配到的 MPN 一页，按每 2 秒一个请求，整个库约 12 小时；实际耗时另行记录。
  3. **重新测量。** 2026-10-06 那批 186 个 MPN 抽样得到的 82% 精确匹配率，是用另一种查询方式测出来的，原始样本也没有保留。正式估算前，要在新索引上重新测量，并提交样本和计算方法。
- **匹配规则：** MPN 在大小写和空白归一化后完全相同，且厂商通过人工审核过的别名表判定一致。立创的品牌字符串带本地名称，例如 `ST(…)` → `STMicroelectronics`。
- **一个 MPN 对应多个 C 编号时：** 先按 Basic > Preferred > Extended，再按是否有货，再按库存多少。仍然分不出来的交给人工复核。
- **输出：** `tools/sourcing_data/lcsc_map.json`，提交到仓库并标注日期。每行包含 MPN、厂商、C 编号、所用规则和快照哈希。
  - 生成器（`gen_passive.py`、`gen_stm32.py`、`gen_esp32.py`）读取这份文件。
  - 手写的包由脚本改写，再运行 `cohdl fmt`。
- **只有映射核实过才发布绑定。** 一个条目的 `supplier lcsc` 子句，要和这个绑定自己的对齐证据（W3）在同一次发布中上线。在此之前映射是未知的，写成 `(0, 0, 0°)` 就是未经核实的声明。所以 W2 先产出映射表，绑定再随 W3 覆盖到相应封装，一个包一个包地上线。

### W3：封装对齐嘉立创坐标系

**目标：** 对每个官方封装 F，以及绑定在它上面的每个 LCSC 料号，嘉立创为该料号使用的封装相对 F 都位于 `(0, 0, 0°)`（RFC-034 §2）。

**证据的单位。** RFC-034 的映射是针对"我们的封装＋供应商某个具体料号的封装"这一对定义的。所以在 F 上验证了一个参考料号，本身并不能说明绑定在 F 上的另一个料号也一样。证据、例外和 CI 检查都按 **（封装, 包版本, 供应商, 料号）** 建立对应关系。

- **范围（按 `329af05` 重新统计）：** 300 个不同的封装（`lib/passive` 之外 285 个，之内 15 个）。大多属于标准封装族：CHIP、SOT、SOD、SOIC/TSSOP、QFP、QFN、BGA。
- **证据：** `tools/sourcing_data/jlc_frames.json`，供 CI 读取，另生成一份 `docs/jlc-frames.md` 供人阅读。每个（封装, 包版本, 供应商, 料号）一行，包含：
  - 记录的映射（目标为 `(0, 0, 0°)`）；
  - 对齐前测得的映射；
  - 证据：方法、日期和凭据（预览截图或测试板记录）；
  - **或者**引用另一行的证据，但必须写明理由。可接受的理由依次为：
    1. 供应商对这两个料号显示同一个封装标识（它的零件页是否提供这种标识，在 W1 期间核实）；
    2. 两个料号放在同一块对齐测试板上，并在同一次预览中检查过。

  没有这类理由的料号，必须有自己的证据。共用证据的一组料号，还要从中直接抽查：至少 3 个，或 5%，取较大者。
- **方法：** 每批做一块对齐测试板。
  - 每个料号放一个实例、角度为 0°，把 BOM 和坐标文件上传到嘉立创的贴片下单流程。预览可以一次显示很多零件，不需要真正下单。
  - 贴片预览截图随该批次存档。
  - 单个零件可以退而人工查看嘉立创商品页来核对。
- **改动方式：** 对整个封装做刚体旋转和平移，焊盘、courtyard 和丝印一起变。焊盘编号和焊盘尺寸绝不改变。
- **pin 1 与极性：** 对齐后，pin 1 或极性标记必须出现在嘉立创预览期望的位置。如果不是，回到厂商文档核查：要么是我们错了（修正，比如 #48），要么这个零件是例外。
- **例外：** 供应商封装与我们的封装合理地不一致的料号，保留非零映射。例外按（封装, 版本, 供应商, 料号）逐条登记并写明理由，因为同一封装下的两个料号可能不同。已知例子：SK6812MINI-E，反贴件，已经量产验证。
- **版本：** 封装有移动的包一律发新版本，不做兼容层。
  - **为什么是破坏性改动。** 移动封装坐标系，会悄悄移动所有用 `place … at … rotate …` 放置它的使用方的铜皮。设计照样能通过检查，不会报任何诊断。
  - **版本号。** 所以要按破坏性改动升版本：升主版本号；包还在 `0.x` 时升次版本号。绝不能只升补丁号。
  - 旧版本在 registry 上保持不可变，已有的锁文件继续解析到旧版本。
  - 发布说明以 RFC-034 §2 的三元组 `(dx, dy, r)` 列出每个被移动封装从旧坐标系到新坐标系的变化量。
  - **`tools/realign_place.py`。** 读取这张变化量表，改写使用方的 `place` 语句，让铜皮保持在原位。新的放置是旧放置与变化量按 §2 同一套 `compose_place` 规则组合的结果。没有 `place` 这些封装的设计不受影响。
  - 仓库内的设计在同一次改动中用这个工具更新，并对比生成的板子，证明铜皮没有移动。
- **顺序：** 先处理 2026-10-06 那次 33 个料的对比中发现方向不同的那 14 个所属的封装族（那次对比的原始数据没有保留，第一块对齐测试板会重新测量这 33 个料并提交结果），再处理已绑定和常用的零件，最后处理其余的。

### W4：按清单补料

优先级跟随快照：Basic（351）→ Preferred（1235）→ 扩展库按需（来源是 registry 的 `component_requests`，以及将来记录下来的搜索未命中）。每个新零件按 `LIBRARY.md` 的流程：

1. **手册：** 从厂商官网获取。官网无法下载时，使用 LCSC 提供的厂商原版文档，记录两个 URL 和 SHA-256。
2. **器件和焊盘图形：** 依据该文档绘制。
3. **封装坐标系：** 一开始就和嘉立创对齐（W3）。
4. **绑定：** 在同一次改动中写上 `supplier lcsc "<C 编号>"`，使用默认映射 `(0, 0, 0°)`。

## 库 CI（官方包）

随各工作线落地，逐步加入 `tests/library.rs`：

- 每个 `supplier lcsc` 料号都必须出现在 `lcsc_map.json` 中，且 MPN 和厂商一致。
- 每个 `supplier lcsc` 绑定在 `jlc_frames.json` 中都有对应的（封装, 包版本, 供应商, 料号）一行。
- 该行的映射与绑定的 `at`/`rotate` 一致；非零映射必须是针对这个确切键登记的例外。
- 每一行要么有自己的证据，要么引用了另一行的证据并写明可接受的理由。
- 封装被移动（包版本更新）后，相关的行在重新核实或重新引用之前失效。

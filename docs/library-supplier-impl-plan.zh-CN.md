# 官方库供应商计划：实施计划

> 中文版，以英文版 [`library-supplier-impl-plan.md`](library-supplier-impl-plan.md) 为准。

状态：草案，2026-10-29；同日根据审查意见修订（A0、封装数、`realign_place.py` 的范围、版本级联、A6 验收、时间线）。本文把 [`library-supplier-plan.md`](library-supplier-plan.zh-CN.md)（下称"库计划"）拆成可以一项一项派出去的工作。每项写明先后、产出和验收，并标出需要人参与的步骤。文中数字来自 2026-10-29 对 `feat/rfc-034` 的只读调研。

角色：**实现者**负责改动；**复验者**在合入前独立重跑检查（第 6 节）。"维护者"指库计划指定的库维护者。

### 决定 W0 工作量的调研结果

- `tests/library.rs` 只有一个测试函数，分三层：
  - 全部 62 个包：声明、文档、E807、按引脚的焊盘重叠；
  - 只有 `@contrib/` 和 `@sifli/`：courtyard 必须是矩形且包住全部焊盘、不同编号的焊盘不得重叠、MPN 和厂商非空、QFN 隔离清单；
  - 一份 46 条、按零件条目登记的白名单。
- 把严格层直接扩到全部包，会遇到四个问题：
  - 白名单按条目登记。`passive` 有 17,431 条、`@st/stm32` 有 3,303 条，没法这样登记。
  - `lib/misc` 有 3 个圆形 courtyard，过不了"只接受矩形"的断言。
  - 重叠检查会跳过 19 个 45°/315° 的焊盘（ESP32 生成的封装，以及 `@contrib/ldo` 的 RT9080）。
  - 检查按 `pub part` 遍历，只提供封装的包（`bga`、`csp`、`qfn`、`qfp`、`soic`）永远查不到。
- `fpc.cohdl` 里的"占位"封装其实都有焊盘，只是画成了通用焊盘，不是空封装：
  - FH12-24S 缺两只固定脚；
  - FH12-10S 的注释写"两排"，实际只画了一排；
  - CONMHF4 只有一个焊盘；
  - YZP0048 是四个圆焊盘。
  
  `lib/connectors/docs/` 里有 FH12、CONMHF4、YZP0048、JST-XH 的 PDF。没有任何设计用到这些零件。`CONN_MIC_2P` 和 `CONN_SPK_2P` 是 `lib/` 里仅有的两个 `mfr: "Generic"` 条目，MPN 都是编的。
- 三个生成器都没有插入额外 AVL 子句的入口：
  - `gen_passive.py` 的测试只拷贝 `tools/passive_data/`；
  - `gen_stm32.py` 对 AVL 行的键做严格校验，多一个键就报错；
  - `gen_esp32.py` 只生成主料。
- E813 只在一次编译的依赖闭包内检查 `(supplier, PN)` 的唯一性。库测试按包分别编译，所以 `lib/` 里两个包之间的冲突发现不了。
- registry 已有 `PUT /api/admin/suppliers/{id}/snapshot`：
  - 整个目录整表替换；
  - 单次最多 10,000 行或 4 MiB；
  - 需要官方账号的会话；
  - 目前没有任何客户端调用它。

  B1 W1 基线快照
  B2 W2 料号映射表

  C2 已知方向不同的 14 个封装族
  C3 其余封装族
阶段 D（发布）                    依赖 RFC-034 合入并发版、B2、C

  D2 registry：lcsc 供应商与目录上传

有两道门槛不在库工作内部，但会卡住发布：

1. **RFC-034 合入并发版。** 带 `supplier` 子句的包，要编译器支持这个语法才能用。
2. **贴片厂预览要人来做。** 每块对齐板都要有人上传、核对。这是整个计划里最慢的一环，见第 5 节。

## 3. 工作项

估算只算实现者的工时加复验，不含等人的时间。

### 阶段 A：离线

**A0 · 分支上远端**，约半天，需先批准

- 把 `feat/rfc-034` 更新到 `main`（v0.9.0），推送，开 draft PR。A4、A5 要写带 `supplier` 子句的 fixture，只有这个分支能编译。
- 候选数据已连同哈希提交，PR 说明里再列一遍。
- 验收：更新后的分支全量测试通过；PR 相对 `main` 的改动只有 RFC-034 和计划文档。

**A1 · 几何审计扩到全部包（W0 主体）**，约 3–4 天

- 审计单位从"零件条目"改为"封装"：遍历每个包声明的全部 `footprint`，只提供封装的包也包括在内。
- 重叠检查支持任意角度的焊盘（矩形和圆角矩形用分离轴法）。保留现有按引脚判定的规则：同一引脚的焊盘（例如拆分的 EP 铜岛）允许重叠，ESP32 生成的封装依赖这一点。
- courtyard 允许圆形（每个焊盘角点到圆心的距离不超过半径）。重画 `lib/misc` 的 3 个会改变几何、触发版本升级，而有两个示例锁定了 `misc = "0.1.1"`。
- 把检查从那个很长的单个测试函数拆到 `tests/library/geometry.rs` 之类的模块，但保留测试名 `every_shipped_component_library_has_consistent_part_footprints`，`LIBRARY.md` 按这个名字引用它。
- 白名单改为按 `(包, 封装, 版本)` 登记，每条写明理由。
- 修复审计暴露出的问题。修不了的进隔离清单，并附 issue。
- 验收：
  - 62 个包要么都通过严格层，要么在隔离清单里；
  - 每条新检查都有反例测试（故意造出重叠、造出 courtyard 越界），必须报错；
  - `cargo test` 全部通过；`git diff --stat` 只涉及 `tests/` 和被修的包。
- 拆成三项：
  - A1a：审计本身和反例测试；
  - A1b：`lib/misc`、旋转焊盘、`@contrib/ldo`；
  - A1c：其余包的批量修复。

**A2 · fpc 连接器**，约 1.5 天，需要先做一个决定

- 依据仓库里的 PDF，画出 FH12-24S 和 FH12-10S（参照已审核过的 FH12-26S）、CONMHF4、YZP0048 的真实焊盘。
- 验收：每个焊盘与 PDF 推荐焊盘的偏差都在 0.01 mm 以内，PR 说明里附逐个焊盘的对照表；A1 的审计通过。
- **2026-10-29 已决定：** `CONN_MIC_2P`/`CONN_SPK_2P` 保留，改为 `#[source_unspecified("mpn")]` 加 `mpn: ""`。没有设计在用它们，改动小，而且如实表示"未知"。

**A3 · 共用抓取客户端**，约 1 天，不发出任何真实请求

- 新建 `tools/sourcing/http.py`，实现库计划"基本规则"里的全部要求：
  - 每个站点每 2 秒最多 1 个请求，每次运行设请求总数上限；
  - 按 URL 缓存，输出为带日期的快照；
  - 固定的 User-Agent；
  - 遇到 403/429 先退避，连续两次就停止本次运行；
  - robots.txt 禁止的路径（包括 `/api`）**在请求发出前**就拒绝；
  - robots.txt 设了 `Crawl-delay` 时遵守它；
  - 所有 EasyEDA 域名一律拒绝。
- 只保存事实字段，原始页面不进仓库。
- 验收：用本地假服务器写单元测试，覆盖限速、缓存、连续两次即停、robots 拒绝、`Crawl-delay`、EasyEDA 拒绝。所有测试都不访问外网。

**A4 · 库 CI 骨架**，约 1.5 天

- 在 `tests/library.rs` 里加入库计划"库 CI"一节的五条检查。数据为空时这些检查空跑通过。
- 确定 `lcsc_map.json` 和 `jlc_frames.json` 的格式（带 `schema_version`），并做格式校验。
- 新增全库唯一性检查：在整个 `lib/` 范围内，一个 `(supplier, PN)` 只能对应一个 `(mfr, mpn)`。这补上了 E813 只在单个依赖闭包内检查的缺口。
- 验收：每条检查都有一个故意写错的 fixture，必须报错；在真实库上通过。

**A5 · 生成器入口**，约 2 天

- `gen_passive.py`、`gen_stm32.py`、`gen_esp32.py` 读取 `lcsc_map.json` 和 W3 证据，只为已对齐的封装生成 `supplier lcsc` 子句。
- 放宽 `gen_stm32.py` 对键的严格校验；`gen_passive.py` 的测试改为也拷贝映射文件。
- 映射为空时，输出必须和现在逐字节相同，这就是回归测试。
- 验收：
  - 空映射时，三个生成器的 `--check` 都通过，`git diff` 为空；
  - 放入一条假映射，只多出对应的那一条子句；
  - 生成的子句能通过编译，E813 也通过。

**A6 · W3 工具**，约 2–3 天

- `tools/jlc_frame_board.py`：输入一份 `(封装, 料号)` 清单，生成一块对齐测试板，产出：
  - CoHDL 工程；
  - Gerber 和钻孔文件，以板框角点为原点；
  - BOM 和 CPL；
  - 一份核对清单，写明每个元件 pin 1 的方位。
  
  每个料号放一份顶面 0°；面别有影响的，再加一份底面的作对照。
- `tools/realign_place.py`：读取 `(dx, dy, r)` 变化量表，按 RFC-034 §2 的 `compose_place` 改写使用方的 `place` 语句。
  - 只改写字面量形式的 `place`，包括 `place mounting[0] at …` 这样带下标的。带表达式的、在 `for` 循环里的、在 `subdesign` 内部的 `place` 都不改写：工具报错并逐条列出，交给人处理。
  - 仓库里共 52 条 `place`，全在三个示例里；`lib/` 里没有。
  - 判定依据是编译器输出的 `.kicad_pcb` 里改写前后的焊盘坐标（用 `tests/kicad_pcb.rs` 已有的基础设施），不用 Gerber。
- 验收：
  - 对三个示例先正向再逆向执行 `realign_place.py`，结果和原来完全一样，`.kicad_pcb` 的焊盘坐标不变；
  - 用板子生成器重新生成底面测试板，CoHDL 自身产物（`.kicad_pcb`、BOM、CPL）与现有文件逐字节相同。Gerber 和钻孔文件的字节随 KiCad 版本变化，只记录 `kicad-cli` 版本和哈希；
  - 需要 `pcbnew` 的 Python 测试用 mock 代替（和 `smt_pos.py` 的测试一样），在普通 Python 下也能跑。

### 阶段 B：联网（每次运行都要批准，并有人盯着）

**B1 · W1 基线快照**

- 在各自的 `partdetail` 页面上逐个确认 1,334 个候选。按每 2 秒 1 个请求，约 45 分钟。
- 下载 146 个 parts sitemap 文件，按库计划的规则过滤。约 5 分钟，下载量约 1 GB。
- 产出：`tools/jlc_catalog.py`，以及第一份带日期和哈希的快照，附来源清单和过滤后的总数。
- 候选里缺了约 250 个 Preferred 料，由维护者在浏览器里翻筛选页补上，约 32 页。是否同时向供应商要官方清单，待决定。

**B2 · W2 料号映射表**

- 先用 sitemap 和 jlcparts 离线建索引，再逐个在 `partdetail` 页面上确认候选。整个库按每 2 秒 1 个请求约需 12 小时，分几个晚上跑。
- 先用 200 个 MPN 的抽样重新测量匹配率，把抽样和方法一起提交，再决定是否全量跑。
- 产出：`tools/lcsc_backfill.py`、`tools/sourcing_data/lcsc_map.json`，以及一份待人工复核的清单。
- 厂商别名：由工具提出建议，人工审核后才生效。

### 阶段 C：对齐证据（贴片厂预览）

**C1 · 底面约定与第一块对齐板。** 2026-10-29 完成，共三轮预览。测试板上四种元件（SOT-23、SOIC-8、0603、0805）各放在顶面 0°、顶面 37°、底面 0°、底面 37° 四个位置。它的编译器 CPL 和 `smt_pos.py --map` 的输出、KiCad 自己导出的坐标都一致。判读规则：顶面已经出现、并且底面一模一样重复的偏差，是封装坐标系的偏移（W3）；只有底面那几份出错，才是底面约定的问题（RFC-034）。

结果（`jlc_frames.json` 的第一批条目）：

| 封装 | 料号 | 坐标系偏差 |
|---|---|---|
| `transistor::FP_JSCJ_SOT23` | C2146 | `rotate 90` |
| `soic::SOIC8P127X790X216N` | C97521 | `rotate 270` |
| `passive::CHIP_0603` | C107045 | 无 |
| `passive::CHIP_0805` | C107110 | 无 |

CPL 用 `--bottom-rotation lcsc=mirrored` 导出后，底面各份（包括 37° 的）全部对齐。因此库的供应商 CPL 一律带这个参数导出；A6 的板子生成器和 C2/C3 的对齐板都用它。

**C2 · 已知方向不同的 14 个封装族**

- 第一块正式对齐板，同时重新测量 2026-10-06 对比过的那 33 个料（原始数据没有保留）。
- 每块板放 30–60 个料号，一次预览看完。
- 预计 3–5 块板，每块需要人花约 15 分钟：上传、截图、回报。
- 第 1 块板再放一个原点不在焊盘几何中心的封装（例如连接器），作为 CPL 位置口径的对照（RFC-034 §3.1）。

**C3 · 其余封装族**

- 按库计划的共用证据规则：阻容按供应商的封装标识分组，每组至少抽查 3 个或 5%，取较大者。
- 板子数量等 B2 统计出绑定数后重算，粗估 15–40 块。

流程：
1. 用 A6 的工具生成测试板。
2. 由人上传并截图。
3. 复验者把测量值和截图记进 `jlc_frames.json`。
4. 实现者对需要的封装做刚体变换，并升包版本。
5. 所有依赖它的包也都发新版本，并用 `cohdl update` 刷新各自的 lock（RFC-029 精确版本、registry 不可变）。`soic`、`qfn`、`qfp`、`bga`、`csp` 里的一个封装最多波及 12 个包和 3 个示例。
6. 用 `realign_place.py` 改写仓库里的设计。
7. A1 和 A4 的检查通过。

### 阶段 D：发布

- **D1：** 一个包一个包地发布。只有映射已确认、对齐证据齐全、CI 通过的包才发。顺序按库计划：先 14 个封装族，再常用件。每个封装族发布时附一份级联清单：封装所在的包，以及所有因此发新版本的依赖包。registry 要先部署 RFC-034 版本，再发第一个带绑定的包：它的搜索从 API docs 读 `suppliers`，更早发布的绑定在 registry 上看不到。
- **D2：**
  - 新增 `lcsc` 供应商这一行。
  - 新增 `tools/upload_supplier_snapshot.py`：读取快照，每次请求最多发 10,000 行；超过就拆开上传，或者先改接口。用官方账号认证。
  - 上传别名表。
  - 每次上传到正式 registry，都要有人明确签字确认。

### 阶段 E：W4 补料

按库计划的四批进行：

| 批次 | 估算 |
|---|---|
| 阻容 | 2–3 人周 |
| 封装族库 | 1.5–2 人周 |
| 分立器件 | 5–8 人周 |
| 常用 IC | 7–11 人周 |

每个新零件都要同时备齐手册、焊盘、对齐和绑定，所以阶段 E 的节奏和阶段 C 一样，受限于预览。等 D1 完整跑通后，再拆成具体工作项。

| 5–6 | B2 全量（夜间）；C2 收尾；D1 第一批 | RFC-034 合入并发版；registry 部署；D2 上传签字确认 |
| 之后 | C3、阶段 E | 每周 1–3 块板 |

阶段 A 大约 2.5–3 周；初稿排的两周，每周都有 5.5–6.5 人日。之后的进度取决于有人能做多少预览，以及 RFC-034 什么时候发版。

## 5. 风险

| 风险 | 对策 |
|---|---|
| 预览吞吐量（W3 证据最多约 17,000 个绑定） | 每块板放满；按供应商的封装标识共用证据，并抽查；先做常用件 |
| 供应商页面改版或限流 | A3 遇到连续两次 403/429 就停；快照带日期，可以续跑；不换 IP，不用代理 |
| 移动封装会悄悄挪动使用方的铜皮 | 按破坏性改动升版本并连带依赖包（D1 的级联清单），配合 `realign_place.py`，再加一个基于 `.kicad_pcb` 焊盘坐标的"铜皮不动"回归测试 |
| 测试和实现犯同一个错，所以全部通过 | 每项都指定一个独立参照：PDF 推荐焊盘、KiCad 自己的导出、反例 fixture |
| 白名单变成什么都放行 | 每条按 `(包, 封装, 版本)` 登记并写明理由；复验者逐条审 |

## 6. 复验清单（每项都做）

- 重跑 `cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`；Python 工具跑 `python3 -I -m unittest`。
- 生成器相关的项：`--check` 没有差异，或者差异正好是该项预期的那些。
- 封装相关的项：逐个焊盘对照 PDF；在 KiCad 里打开生成的板子跑 DRC；`smt_pos.py --map` 通过。
- 抓取相关的项：读请求日志，确认限速、User-Agent 和请求上限都生效，并且没有出现 `/api` 或 EasyEDA 的地址。
- 改动范围以 `git diff --stat` 为准，不以该项自己的汇报为准。
